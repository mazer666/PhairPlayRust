## 2. The result of the untouched commit

**The test suite of the untouched commit does not finish.**

The run hangs in the test
`engine::tests::starting_binds_the_listener_and_advertises_the_service` of
the crate `phairplay-cast`. The reason is a deadlock:

```rust
let services = registrar.services.lock().expect("lock");   // the lock is held
assert_eq!(services.len(), 1);
assert_eq!(services[0].service_type, "_googlecast._tcp");
engine.stop().await.expect("stop");                         // stop() locks it again
```

`CastEngine::stop()` withdraws the advertised service, and
`RecordingRegistrar::unregister()` locks the very same mutex. The guard of
the lock is still alive, the mutex is not reentrant, and the test waits
forever.

The reproduction is a test of its own; it was run against the untouched
commit and it hangs in exactly the same way:

```text
PROBE: about to hold the lock and then stop
PROBE: the lock is held, calling stop -> deadlock
<the process was killed after 25 seconds>
```

**Consequence for the gate:** a job of the continuous integration that runs
the tests of the workspace never ends. The job needs a timeout, and the
timeout of the job is the only thing that ends the run. A test suite that
does not terminate is a gate that does not exist.

## 4. The thirteen failures of the baseline

### 4.1 Two unit tests of the dashboard (`phairplay-web`)

```text
---- api::tests::an_unknown_protocol_is_a_not_found stdout ----
thread 'api::tests::an_unknown_protocol_is_a_not_found' panicked at
  tokio-1.54.1/src/runtime/blocking/shutdown.rs:51:21:
Cannot drop a runtime in a context where blocking is not allowed. This happens
when a runtime is dropped from within an asynchronous context.
---- api::tests::the_status_is_answered stdout ----
```

**Cause:** `AppState` owns a `ReceiverCore`, and the `ReceiverCore` owns a
Tokio runtime. Tokio refuses to drop a runtime inside an asynchronous
context — the runtime wants to block the worker thread while it shuts its
blocking pool down — and the panic comes out of the `Drop` of the runtime.

**Why it is a defect and not a test artefact:** the same thing happens in
the product. A host that drops the receiver inside a coroutine — a Kotlin
coroutine, a Swift task, a callback of a native shell — takes the whole
process down with it. The fix is in the bridge, not in the test: the
runtime of the bridge is now shut down with `shutdown_background()`, which
does not block the thread that drops the receiver.

## 5. The warnings of the baseline

```text
warning: unused return value of `clone` that must be used
  --> engines/cast/src/tls.rs:109:9
warning: trait `MustErr` is never used
  --> apps/web/src/test_support.rs:32:18
```

Both are turned into errors by `cargo clippy --workspace --all-targets --
-D warnings`, which is the lint of the gate. The lint of the workspace was
therefore **red** on the baseline as well — the baseline was never green.

The number of the clippy findings of the baseline was measured on the
worktree of the commit with

```text
cargo clippy --workspace --all-targets --keep-going --message-format=short -- -D warnings
```

One finding had to be repaired first — `core/phairplay-core/src/session.rs`
carries a `#[must_use]` on a function that already returns a `#[must_use]`
type, and the crate does not compile with that finding — otherwise the
check stops at the first crate and never reaches the other ten.

| Lint | Number of findings |
|---|---|
| `expect_used` / `unwrap_used` (on a `Result`) | 297 |
| `expect_used` / `unwrap_used` (on an `Option`) | 39 |
| `field_reassign_with_default` | 5 |

The dominant group is the first one: the test modules of the workspace used
`expect()` and `unwrap()` although the workspace denies both — and the

`#![allow(clippy::expect_used, clippy::unwrap_used)]` that the integration
tests of the repository already carried.
