PhairRust

One receiver for AirPlay 2, Miracast, Google Cast and DLNA/UPnP. It runs on your machine, speaks only to the devices on your local network — and asks for nothing: no account, no advertising, no telemetry, no cloud.

The promises

Four things this project does not do

A receiver sits between your phone and your screen. Everything it does can be watched — that is the point of a self-hosted receiver. These four promises are the reason the project exists.

No account

No registration, no login, no licence server to call. You install the receiver, it shows up on your network, and that is the whole setup.

No advertising

No ads, no sponsored entries, no partner integrations, no telemetry SDK. The project is not funded by advertising, and nothing in the code talks to an advertiser.

No telemetry

The receiver does not measure what you play, does not report usage anywhere and does not write statistics outside your machine. The only data it produces is the picture and the sound you asked for.

No cloud lock-in

The receiver works with the network cable unplugged. There is no server in the middle that could change, throttle or switch the project off — you run the code, you own the result.

The protocols

What the receivers speak

Four protocol engines share one core: the same session model, the same counters, the same hardening rules. Each engine advertises itself on the local network and accepts a sender from it.

The protocols PhairPlayRust implements, with their discovery service, their transport, the media they carry and their specific rules.
Protocol Discovery Transport Media Rule
AirPlay 2 _airplay._tcp, _raop._tcp RTSP with RTP over UDP H.264 video, AAC-LC / AAC-ELD, Apple Lossless One sender at a time
Miracast / WFD _miracast._tcp RTSP control plane with RTP H.264 video, Linear PCM One sender at a time
Google Cast _googlecast._tcp CastV2 over TLS H.264, VP8, AAC-LC, MP3, Linear PCM Several senders at a time
DLNA / UPnP SSDP HTTP with SOAP and GENA Audio playback: AAC, Opus, MP3, FLAC, Linear PCM One sender at a time

AirPlay advertises two service types: a receiver that only announces _airplay._tcp stays invisible to some senders. Google Cast is the documented exception to the one-sender rule — a Cast receiver may serve several senders at once.

The architecture

Five layers, one direction

Dependencies point strictly downwards. A format crate never knows a protocol, a protocol never reaches into the platform, and the core never knows an engine exists. The rule is written down in docs/design/BUILD-CONTRACT.md and every crate is built against it.

The quickstart

From a clone to a running receiver

The project is a plain Cargo workspace. There is no installer, no service installer and no account to create.

Get the source

The repository contains the whole stack: the core, the four engines, the formats and the dashboard.

git clone https://github.com/mazer666/PhairPlayRust.git
cd PhairPlayRust

Build it and run the tests

Every crate is tested, including the negative tests that attack the parsers. The build contract is the reference for how the workspace is put together. 

cargo build --release
cargo test --workspace

Start the receiver

The web application starts the engines, serves the dashboard and binds to the loopback interface only — the panel is a local tool, not a network service. 

cargo run --release --manifest-path apps/web/Cargo.toml

Open the dashboard

The panel is served on the loopback address of the process. It shows the state of the four receivers, the live sessions, the throughput of the running stream and the codec reference — and it can switch a receiver on or off.

Known limits. FairPlay-protected streams stay encrypted: the receiver cannot decrypt DRM content. AirPlay 2, Miracast and DLNA accept one sender at a time; Google Cast is the documented exception and serves several senders at once. The dashboard always states which of the two you are looking at.

The threat model

Every device on your network is untrusted

A receiver on a home network is reachable by every device on it. The threat model says so, and the limits in the code follow from it.

  • Every network input is length-limited, header-limited and timeout-bound.
  • Parsers reject malformed input instead of guessing what was meant.
  • Queues are bounded by a frame count and by a byte budget.
  • The DLNA engine refuses external entities and callback addresses outside the local subnet.
  • The dashboard is served on the loopback interface; no other device can reach it.
